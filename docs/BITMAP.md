# RowPack 紧凑存储与位级编码设计方案

**文档版本：** V1.0  
**设计目标：** 在保证随机读取、并发读取、数据完整性和格式可扩展性的前提下，尽可能减少 RowPack 的文件体积。

---

## 一、设计目标

RowPack 是一个面向二维表数据的 Go 存储引擎，计划支持：

1. 单文件或数据文件与索引文件分离的存储方式。
2. 高效的块级读取与随机访问。
3. 并发读取及受控的并发写入。
4. 数据压缩与可选加密。
5. 数据快照、增量快照和数据块复用。
6. 面向不同数据类型的可选编码方式。

本方案重点解决数据编码、元数据、索引及快照结构中的冗余问题。

### 1.1 核心原则

- **先消除冗余，再进行压缩。**
- **优先优化高频、重复出现的元数据。**
- **按块独立解码，避免随机读取依赖整个文件的解压。**
- **根据数据特征选择编码方式，不强制所有列采用同一种编码。**
- **磁盘格式与 Go 内存数据结构分离。**
- **保持数据格式具有明确的版本和演进机制。**

### 1.2 非目标

第一阶段不追求所有字段都达到理论最小存储空间，也不要求实现复杂的通用压缩算法。

优先实现简单、可测试、能明确评估收益的优化。

---

## 二、整体存储架构

建议将 RowPack 的存储体系分为四层。

### 2.1 逻辑数据层

对外提供统一的二维表数据接口。

逻辑数据可以包含：

- Schema。
- 行数据。
- 主键定义。
- 数据块。
- 快照及增量变更。

上层 API 不需要感知某一列具体采用了哪种压缩或编码算法。

### 2.2 编码层

负责将逻辑数据转换为紧凑的二进制表示。

支持以下编码：

| 编码方式 | 适用数据 |
|---|---|
| Plain | 普通整数、字符串及暂不支持专用编码的类型 |
| Null Bitmap | 可空字段 |
| Boolean Bitmap | 布尔字段 |
| Varint | 大小差异明显的整数 |
| Delta | 排序整数、主键、时间戳 |
| Bit Packing | 数值范围较小的整数 |
| Dictionary | 低基数、高重复率字段 |
| Prefix Compression | 适合前缀共享的字符串 |
| Run-Length Encoding | 连续重复值 |

编码器必须能够独立测试，不依赖具体文件布局。

### 2.3 块压缩层

编码完成后，将块数据交给压缩器。

第一阶段建议支持：

- 不压缩。
- Zstandard（Zstd）。

压缩器不需要了解列的业务含义。

是否压缩应由数据块大小、压缩收益和性能策略决定，而不是固定对所有小块执行压缩。

### 2.4 存储与索引层

负责：

- 数据块定位。
- 文件偏移量管理。
- 索引读取。
- 数据块写入。
- 快照引用。
- 完整性验证。

索引采用适合随机访问的独立编码策略，避免为了节省空间而导致每次读取都必须解压整个索引文件。

## 三、推荐的数据块格式

第一阶段建议采用**块级自描述格式 + 列级可选编码**。

这里的自描述是指块头或块元数据能够明确指出编码类型、数据长度和必要的解码参数，而不是要求每个字段都重复保存完整类型信息。

### 3.1 数据块结构

```text
RowPack File
│
├── File Header
│   ├── Magic
│   ├── Format Version
│   └── File Flags
│
├── Schema Metadata
│   ├── Column Definitions
│   ├── Column Types
│   ├── Nullability
│   └── Primary Key Definition
│
├── Data Blocks
│   ├── Block Header
│   ├── Column Metadata
│   ├── Encoded Payload
│   └── Integrity Metadata
│
├── Snapshot Metadata
│
└── Index
    ├── Block Locations
    ├── Primary Key Ranges
    └── Snapshot References
```

如果采用独立索引文件，则将索引结构放入对应的索引文件中。

具体的元数据放置位置可以调整，但必须避免在文件头、Schema、数据块和索引中重复保存相同信息。

### 3.2 Block Header

建议包含：

| 字段 | 用途 |
|---|---|
| Version | 数据块格式版本 |
| Flags | 块属性标志 |
| Row Count | 行数 |
| Column Count | 列数或列组数量 |
| Metadata Length | 元数据长度 |
| Encoded Length | 编码后数据长度 |
| Compressed Length | 压缩后数据长度 |
| Codec | 压缩算法标识 |
| Checksum Type | 完整性校验算法标识 |

具体字段可以根据实际格式进行合并或调整。

长度字段必须明确其单位和对应的数据处理阶段。

例如，Encoded Length 表示编码后的长度，Compressed Length 表示压缩后的长度，不能混用。

如果加密采用 AES-GCM，还必须明确记录或推导 nonce、认证标签及密文长度，并保证 nonce 在同一密钥下不重复。

### 3.3 Flags 位掩码

块级状态使用位掩码，而不是多个独立的布尔字段。

例如：

```go
type BlockFlags uint16

const (
    FlagHasNullBitmap BlockFlags = 1 << iota
    FlagHasDictionary
    FlagSortedByPrimaryKey
    FlagIsDelta
    FlagIsEncrypted
    FlagHasChecksum
)
```

说明：

- 每个标志占用一个 bit。
- 多个标志可以组合。
- 未知标志的处理规则必须由格式版本和兼容性约定确定。
- Go 的内存布局不是磁盘格式，序列化时必须显式指定字节序和字段宽度。

如果所有标志都能放入一个字节，则可以使用 `uint8`；不要为了追求位压缩而让编码逻辑变得复杂。

## 四、Null Bitmap 与 Boolean Bitmap

这是第一阶段最值得实现的位级优化。

### 4.1 Null Bitmap

对于可空字段，不建议在每个值前面都写入一个独立的空值标志。

改为每列或每个列组保存一张位图。

例如：

```text
数据：
[10, NULL, 20, 30, NULL, 40, 50, 60]

Null Bitmap：
01001000
```

上面的位序仅作示意，正式格式必须明确规定 bit 0 对应哪一行，以及字节内部的位序。

每行一个 bit：

- 0：非 NULL。
- 1：NULL。

对于 8 行数据，位图只占 1 字节。

对于 10,000 行数据，位图占：

```text
ceil(10000 / 8) = 1250 bytes
```

不需要额外的逐值标志字节。

### 4.2 NULL 值的载荷处理

NULL 对应的数据值不应再占用普通值的存储空间。

例如：

```text
Logical Values:
[10, NULL, 20, NULL, 30]

Null Bitmap:
01010

Encoded Values:
[10, 20, 30]
```

实际格式必须规定：

1. 编码载荷中是否跳过 NULL。
2. 如何根据位图恢复行位置。
3. NULL 与空字符串、零值的区别。
4. 解码时如何恢复原始行顺序。

对于不支持 NULL 的字段，可以直接省略 Null Bitmap。

### 4.3 Boolean Bitmap

布尔字段直接使用位图。

```text
[true, false, true, true, false, false, true, false]

Bitmap:
10011010
```

这里同样仅为示意，实际位序由格式规范确定。

每个布尔值只需要 1 bit，而不是至少 1 字节。

如果布尔列可空，可以同时保存：

- Null Bitmap。
- Boolean Bitmap。

Boolean Bitmap 中对应 NULL 行的值应被视为无效，不得与真实的 `false` 混淆。

## 五、整数编码策略

整数编码应根据数据分布选择，不建议统一采用一种算法。

### 5.1 Varint

适用于数值大小差异较大、编码实现需要保持简单的场景。

优点：

- 易于实现。
- 小整数占用空间少。
- 适合长度不固定的整数。

缺点：

- 需要逐个解码。
- 随机定位单个整数时，通常需要额外的偏移信息。
- 对连续的小整数，可能不如 Bit Packing 紧凑。

### 5.2 Delta Encoding

适用于排序主键、递增序号和单调时间戳。

例如：

```text
Original:
1000, 1001, 1002, 1003, 1004

Delta:
1000, 1, 1, 1, 1
```

第一个值保存基值，后续值保存相邻差值。

对于可能递减的数值，可以使用有符号差值或 ZigZag 等适当编码。

对于存在重复值的序列，Delta 允许出现零差值。

注意：

- 差值必须采用足够宽的整数类型计算，避免有符号溢出。
- 主键的排序顺序必须与实际比较语义一致。
- 不能直接假设所有数据库主键都为整数。

### 5.3 Bit Packing

对于一组已知范围的非负整数，使用统一位宽打包。

设一组整数的最大值为 `maxValue`，则表示该组数值所需的最小位宽为：

```text
bitWidth = ceil(log2(maxValue + 1))
```

如果全部数值都是 0，则可使用 0 位载荷并在元数据中明确表示该组为常量。

例如：

```text
Values:
[0, 1, 3, 2, 7, 4, 1, 0]

Maximum:
7

Required Width:
3 bits
```

8 个整数只需要：

```text
8 × 3 = 24 bits
```

即 3 字节，不包含块头和编码元数据。

### 5.4 Delta + Bit Packing

对于排序整数，建议优先测试：

```text
Base Value
    ↓
Delta Values
    ↓
Bit Width
    ↓
Bit-Packed Payload
```

解码时：

1. 读取基值。
2. 解码差值。
3. 累加恢复原始值。

适合主键范围索引和块内有序整数列。

但不应强制用于随机分布或差值很大的数据。

### 5.5 分组位打包

不建议为整个大文件只计算一个统一位宽。

建议在块内进一步分组，例如每 128 或 256 个整数计算一个位宽。

每组保存：

- 基值或必要的差值起点。
- 位宽。
- 元素数量。
- 编码载荷。

这样可以减少极端值导致整列位宽上升的问题。

分组大小应通过基准测试确定，不应直接固化为不可变的格式限制。

## 六、Dictionary Encoding

对于重复率较高的字符串或枚举值，采用字典编码。

例如：

```text
Original:
["SUCCESS", "FAILED", "SUCCESS", "SUCCESS", "FAILED"]

Dictionary:
0 = "SUCCESS"
1 = "FAILED"

Encoded IDs:
[0, 1, 0, 0, 1]
```

如果字典只有 2 个值，每个 ID 只需要 1 bit。

如果字典有 8 个值，每个 ID 只需要 3 bits。

建议优先测试：

- 状态字段。
- 地区代码。
- 类型名称。
- 重复率较高的短字符串。

不建议对所有字符串强制使用字典编码。

当字典本身较大、重复率较低时，字典和 ID 的额外开销可能高于直接存储。

编码器可以先估算：

```text
Plain Size
Dictionary Size + ID Size
```

只有预估能够获得明确收益时才选择字典编码。

---

## 七、索引紧凑化设计

索引是 RowPack 中应当独立优化的部分。

### 7.1 块级索引

建议优先保存块级元数据：

- 数据块起始偏移量。
- 数据块长度。
- 行数。
- 主键最小值和最大值。
- 所属快照。
- 数据块标识。

尽量避免为每行保存完整的 64 位文件绝对偏移量。

### 7.2 偏移量编码

如果数据块在文件中按顺序排列，可以记录：

```text
First Offset
Offset Delta 1
Offset Delta 2
...
```

其中：

```text
Offset Delta = Current Offset - Previous Offset
```

如果块大小通常远小于整个文件大小，偏移量差值可能更适合 Varint 或固定宽度位打包。

但必须注意：

- 随机访问仍然需要能够快速定位目标块。
- 如果索引压缩后无法直接随机访问，应设计分段索引或索引页。
- 不应为了压缩几个字节而让每次随机读取都必须解码整个索引。

### 7.3 两级索引

对于大文件，可以采用：

```text
Root Index
    ↓
Index Pages
    ↓
Data Blocks
```

根索引保存索引页的定位信息，索引页保存一组数据块的元数据。

这样既可以限制内存占用，也可以控制索引读取粒度。

第一版如果数据规模有限，可以先使用内存索引，待索引规模成为瓶颈后再引入索引页。

### 7.4 哈希策略

数据块的 SHA-256 等完整性哈希不应为了节省少量空间而随意截断。

建议将哈希用于：

- 数据完整性校验。
- 快照块复用。
- 内容去重。
- 写入后的验证。

对于内容寻址，还应考虑哈希算法标识、数据块编码版本，以及哈希究竟针对原始数据还是编码后数据。

## 八、快照和增量数据

RowPack 的快照能力可以进一步减少累计存储量。

### 8.1 变更位图

对于适合稠密表示的变更集合，可以使用位图记录哪些行发生变化。

例如：

```text
0 = 未变化
1 = 已变化
```

但如果变更非常稀疏，保存变化行的 Delta 编码索引可能更省空间。

因此，建议在稠密位图与稀疏索引之间按实际数据特征选择。

### 8.2 Tombstone Bitmap

删除操作可以使用 Tombstone 或删除记录表示。

位图适用于行集合已确定、删除位置相对稠密的情况。

如果删除记录非常稀疏，则应考虑使用紧凑的行号列表。

### 8.3 数据块复用

对于相同内容的数据块，不必在每个快照中重复写入。

可以设计：

```text
Snapshot A
    ├── Block 1
    ├── Block 2
    └── Block 3

Snapshot B
    ├── Reference → Block 1
    ├── Reference → Block 2
    └── New Block 4
```

快照 B 只新增真正发生变化的数据块。

该机制比单纯压缩变更标志更有可能显著减少长期累计空间。

实现时必须考虑：

- 引用关系。
- 崩溃恢复。
- 块的生命周期。
- 快照删除。
- 文件整理和空间回收。
- 数据块哈希碰撞的验证策略。

## 九、压缩与加密顺序

建议采用：

```text
Logical Rows
    ↓
Column Encoding
    ↓
Block Serialization
    ↓
Compression
    ↓
Optional Encryption
    ↓
File Storage
```

原因：

1. 编码先减少数据冗余。
2. 压缩再处理剩余的重复模式。
3. 加密后的数据通常不适合继续压缩。

如果使用 AES-GCM，需要保证：

- nonce 在同一密钥下不重复。
- 认证标签得到正确保存和验证。
- 密文长度与认证信息长度明确记录。
- 索引和元数据中的敏感信息根据威胁模型决定是否加密。
- 文件格式版本和算法标识能够正确识别。

加密、压缩和编码应当是可组合的模块，不要让列编码器直接依赖具体的加密实现。

## 十、Go 实现规范

### 10.1 磁盘格式与 Go struct 分离

不要直接将 Go struct 的内存布局写入文件。

应显式控制：

- 字段宽度。
- 字节序。
- 位序。
- 整数编码。
- 长度字段。
- 对齐规则。
- 版本兼容性。

例如：

```go
type BlockFlags uint16

const (
    FlagHasNullBitmap BlockFlags = 1 << iota
    FlagHasDictionary
    FlagSortedByPrimaryKey
    FlagIsDelta
    FlagIsEncrypted
)
```

实际写入文件时，应显式序列化为规定的字节序。

### 10.2 编码器接口

建议建立独立的列编码接口。

```go
type ColumnEncoder interface {
    Encode(src []any) ([]byte, error)
    Decode(src []byte, rows int) ([]any, error)
}
```

以上仅用于说明接口职责。正式实现时，可以使用类型化的列数据结构，避免所有数据都经过 `[]any`，从而减少装箱和分配开销。

建议提供：

- PlainEncoder。
- NullBitmapEncoder。
- BooleanBitmapEncoder。
- VarintEncoder。
- DeltaBitPackEncoder。
- DictionaryEncoder。

每种编码器应具有独立的单元测试和基准测试。

### 10.3 避免不必要的内存分配

在 Go 中应关注：

- 编码缓冲区复用。
- 减少临时切片。
- 避免重复转换和复制。
- 对常见整数类型提供专用实现。
- 降低接口调用和装箱带来的额外成本。
- 在保证线程安全的前提下复用缓冲区。

不要为了减少磁盘空间而引入大量小对象，导致 GC 压力和解码时间显著上升。

## 十一、文件格式兼容性

紧凑编码会增加格式复杂度，因此必须建立明确的版本机制。

### 11.1 编码标识

每个使用专用编码的列或列组必须能够识别：

- 编码类型。
- 编码版本。
- 元素数量。
- 位宽。
- 必要的基值。
- 字典长度或其他解码参数。

对于不需要某项参数的编码，可以省略该字段。

### 11.2 向前兼容与向后兼容

建议遵循：

1. 新增编码时分配新的编码标识。
2. 不改变既有编码标识的语义。
3. 未知编码必须明确报错，不能按 Plain 数据误读。
4. 对不支持的新格式版本拒绝读取或提供明确的降级机制。
5. 保留必要的迁移工具，避免格式演进后旧文件无法处理。

### 11.3 数据完整性

解码过程必须检查：

- 长度字段是否越界。
- 位宽是否合法。
- 元素数量是否合理。
- 整数计算是否溢出。
- 字典索引是否有效。
- 块是否完整。
- 解压后的大小是否超过允许限制。
- 加密认证是否通过。

---

## 十二、性能与空间测试

不能只通过理论位宽判断优化是否成功。

每项编码都需要测试文件大小和运行性能。

### 12.1 测试数据

至少覆盖：

1. 连续递增整数。
2. 随机整数。
3. 小范围整数。
4. 重复率高的字符串。
5. 随机字符串。
6. 大量 NULL。
7. 大量布尔值。
8. 混合类型二维表。
9. 大量小数据块。
10. 多个累计快照。

### 12.2 记录指标

| 指标 | 目的 |
|---|---|
| 原始数据大小 | 建立基线 |
| 编码后大小 | 衡量编码本身收益 |
| 压缩后大小 | 衡量最终存储收益 |
| 索引大小 | 评估元数据成本 |
| 编码耗时 | 评估写入开销 |
| 解码耗时 | 评估读取开销 |
| 随机读取延迟 | 验证索引与块设计 |
| 并发读取吞吐量 | 验证并发性能 |
| 内存峰值 | 控制资源消耗 |
| GC 开销 | 评估 Go 实现成本 |

### 12.3 对照组

至少比较：

- 当前编码方案。
- 仅使用 Zstd。
- Null Bitmap + Zstd。
- Delta + Bit Packing + Zstd。
- Dictionary + Bit Packing + Zstd。
- 混合编码 + Zstd。

这样才能判断节省空间究竟来自专用编码还是通用压缩。

## 十三、分阶段实施计划

### Phase 1：基础位级优化

实现：

- Block Flags。
- Null Bitmap。
- Boolean Bitmap。
- Schema 类型去重。
- 编码版本标识。
- 编码与解码测试。

目标是以较低的实现成本减少重复元数据和布尔状态的存储空间。

### Phase 2：整数与索引优化

实现：

- Varint。
- Delta Encoding。
- Delta + Bit Packing。
- 紧凑块索引。
- 偏移量差分编码。
- 编码器基准测试。

目标是减少主键、整数列和索引的存储开销。

### Phase 3：自适应编码

实现：

- Dictionary Encoding。
- Run-Length Encoding。
- 按块或列选择编码。
- 编码收益估算。
- 编码策略基准测试。

目标是根据数据特征自动选择编码方式。

### Phase 4：快照与增量优化

实现：

- 增量块。
- 删除记录。
- 数据块复用。
- 内容寻址。
- 快照引用关系。
- 空间回收。

目标是减少累计快照中的重复数据。

## 十四、最终设计建议

RowPack 第一版不应一开始就实现所有压缩算法。

建议优先确定以下原则：

1. Schema 统一保存字段类型，避免每个值重复携带类型信息。
2. 可空字段使用 Null Bitmap。
3. 布尔字段使用 Boolean Bitmap。
4. 块级状态采用 Flags 位掩码。
5. 整数列根据数据特征选择 Plain、Varint、Delta 或 Bit Packing。
6. 重复率高的字符串考虑 Dictionary Encoding。
7. 索引以块级索引为主，必要时采用两级索引。
8. 每个数据块能够独立定位、解码和验证。
9. 编码后再进行 Zstd 压缩，最后进行可选加密。
10. 通过真实数据基准测试决定编码策略，而不是追求理论最小位数。
11. 快照优化应优先考虑未变化数据块的复用。
12. 格式版本、长度边界、溢出检查和完整性校验必须从第一版开始设计。

**最终目标不是打造一个单纯追求最小文件的压缩器，而是建立一个兼顾存储空间、随机读取、并发访问和长期演进的紧凑型数据存储格式。**
