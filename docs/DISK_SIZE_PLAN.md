# 磁盘体积优化计划

本文回答两个问题：磁盘现在被谁占着，以及按什么顺序去压缩它。所有数字来自
`testdata/size-baseline/` 与 `testdata/baseline/` 的实测，不用估算值。

## 1. 现状：磁盘到底被谁占着

样本（scale 1，1 FULL + 20 DELTA，8 表 / 21 快照 / 291 块 / 420,298 逻辑行）：

| 部分 | 字节 | 占比 |
| --- | --- | --- |
| **数据块 payload**（`storedBytes`） | 16,389,743 | **96.5%** |
| IndexTxn 全部 | ~588,000 | 3.5% |
| └ 其中 Row Index 页区 | ~575,000 | ~3.4% |
| └ Fence 目录 + chunk 头/目录 | ~13,000 | ~0.1% |

`rawBytes` 44,813,429，`ratio` 0.366，`bytePerRow` 40.4。

**结论先行：索引压到零也只省 3.5%。** 任何"大幅减少"必须落在数据块上。
索引侧仍有冗余（见 §4-D），但总量不到 5 KB，只配顺带清理。

## 2. 已完成：压缩级别接线（commit 621de72）

`applyDefaults()` 漏了解析 `CompressionLevel`，`format.DefaultCompressionLvl`
全仓库从未被引用，零值泄漏到 `EncoderLevelFromZstd(0)` 的最差档位。补上解析后：

| 档位 | dataBytes | GetCold | WriteFull |
| --- | --- | --- | --- |
| 0（原默认，落 1 档） | 18,657,987 | 53.2 µs | 91.0 ms |
| 3–5 | 17,293,714 | 56.3 µs | 95.2 ms |
| **6–9（已采用）** | **16,986,363** | **50.0 µs** | 107 ms |
| 19 | 16,569,174 | 未测 | 慢得多 |

磁盘 -9.0%，且是唯一让冷读同时变快的档位（-5.9%）。代价是写入吞吐 +17.5%。
再往上到 19 只多省 2.4%，写入却慢得多，不做。

## 3. 候选方向

### A. 行式 tuple → 列式（PAX）

**现状**：Rows Page 的 `[tuple bodies]` 是每行 `null bitmap + 各列值` 紧挨着拼接，
跨行的同列值不相邻，zstd 吃不到列内相似性。

**预期收益**：最大。数字列（counters 60K 行、schedule 15K 行）与低基数列
（lookup 的 code 列，4000 行取值于固定词表）压缩率会显著改善；**随机 blob
（documents 的 512 B × 20K 行）不收益**——它本来就不可压缩，且占了样本很大一块，
这会摊薄整体百分比。

**代价**：读路径大改。整行解码要从"顺序读一段"变成"跨列 gather"，随机点读
很可能变慢，而点读是本项目的稳态热路径。

**工程量**：大。**破坏兼容**——需提升格式版本并新建 golden 样本族。

### B. 跨块 zstd 字典

**现状**：每页独立压缩，无字典。32 KiB 页的窗口偏小，跨块的重复模式
（schema 形状、重复文本、相似值分布）完全没有被利用。

**预期收益**：中等。对小页尤其有效，因为字典正好补窗口的不足。

**代价**：字典要落盘（一次性开销）、解码端要常驻字典（内存）；编码端要么预训练
要么动态训练，都会增加写入路径复杂度。

**工程量**：中。**破坏兼容**——没有字典的老 reader 解不开，需提升版本。

### C. 页大小 32 KiB → 64 KiB

**现状**：`DefaultPageSize = 32 << 10`，由页大小扫描选定，README 记着它比 64 KiB
**只损失约 7% 压缩**，同时把冷读解压量减半。

**预期收益**：天花板就是那 7%，而且是在已经压到 0.366 的基础上再打折扣。

**代价**：冷读解压量翻倍——每个 `Get` 要解 64 KiB 而不是 32 KiB，与"读优先"直接冲突。

**工程量**：极小（改一个常量）。**不破坏兼容**。

### D. 索引侧冗余清理

- 页头 `FirstRowID` 恒等于 `MinRowID`（页内按 RowID 升序）→ 每页白扔 8 B
- `ChangeBitsBytes` 可由 `EntryCount` 推导（`ceil(n/4)`，解析侧已经在校验这个等式）→ 4 B
- Fence 的 `EntryCount` / `PageCRC32C` 与页头重复 → ~8 B/页
- 按表切页后 `TableRunBytes` 恒为单个 run → 可推导

**收益**：237 页 × ~20 B ≈ **5 KB（0.03%）**，不值得单独立项，只配搭别的格式改动顺带做。

## 4. 执行顺序

排序原则：**先用最便宜的办法把最大杠杆的收益测出来，再决定是否动格式。**

### 第 1 步：先量 A 的收益，不碰引擎（低成本、高信息量）

A 是唯一能"大幅"的方向，但它工程量最大、还破坏兼容。在动工之前，应该先用一次
性实验把收益测出来：

- 取样本里收益最大和最小的两个极端表（数字密集的 `counters`、低基数的 `lookup`，
  以及不可压缩的 `documents` 作对照）
- 用临时脚本把它们的 tuple 按列式重排后跑 zstd，与现行行式布局对比压缩率
- **不改引擎、不入版本库**，测完即弃

判据：如果列式对可压缩表收益显著、且按 blob 占比折算后整体仍有两位数百分比，
A 才立项；否则 A 的收益会被不可压缩的 blob 摊薄到不值得动格式。

### 第 2 步：按第 1 步结果二选一

- **A 立项** → 设计 PAX 布局（页内分列段），提升格式版本、新建 golden 样本族。
  重点是保住随机点读：整行解码不能退化成跨列 gather，考虑页内列段 + 段内定长。
- **A 不立项** → 转 B（跨块字典），它工程量更小，同样能补小页的窗口不足。

### 第 3 步：C 只作兜底

页大小改动最便宜，但它能给的就 7% 且直接伤冷读。只有在 A/B 都做完、还想再抠时，
才用一次 A/B 实测（32K vs 64K 的 `dataBytes` 与 `GetCold`）决定，不靠 README 里的旧数字拍板。

### 第 4 步：D 搭车

任何需要提升格式版本的改动里顺手清掉，不单独立项。

## 5. 度量与判定

| 维度 | 命令 |
| --- | --- |
| 磁盘 | `make size-baseline` / `make size-diff OLD=<date> NEW=<date>` |
| 性能 | `make baseline` / `make baseline-diff OLD=<date> NEW=<date>` |

**准入线**（沿用既有约定）：磁盘必须有可测收益，且 `BenchmarkGetCold` 回退不超过
阈值。`BenchmarkWriteFull` 的回退可放宽——写入是批处理路径；`BenchmarkOpenReplay`
是 `Open()+Close()` 的一次性开销，不计入判定。

已知陷阱：`heapAfterOpenBytes` 在 2026-10-10 之前测的是被生成器污染的进程内增量，
与之后的子进程测量**不可直接比较**（详见 `cmd/rowpack-sizesample/main.go` 的
`openHeapCost`）。
