# ADR-001：`.rpk` 是提交权威，`.rpi` 可重建

- 状态：已接受
- 日期：2026-09-06
- 关联规范：REQUIREMENTS.md FR-011、FR-012（原引用 BINARY_FORMAT_V1.md §1/§6/§7，已随 v1 历史文档移除；v2 承接同一原则，见 BINARY_FORMAT_V2.md）

## 背景

RowPack 使用两个持久化文件：`.rpk`（数据）与 `.rpi`（索引）。两文件之间存在
跨文件提交窗口：数据已落盘但索引尚未写完时进程退出，调用者无法仅凭返回值确定
提交结果。若把两文件视为对等权威，恢复时无法消除歧义。

## 决策

1. `.rpk` 中“完整且 CRC 通过的 SnapshotFooter”是快照已提交的唯一权威标志。
2. `.rpi` 只是派生导航结构：其内容可完全从 `.rpk` 重放/重建。
3. 恢复规则固定为：
   - 数据领先索引：扫描尾部完整 Snapshot，读写模式补写索引，只读模式仅建内存索引。
   - 索引领先或尾部损坏：读写模式截断 `.rpi` 至共同提交点；只读模式忽略尾部。
   - 无 Footer 的数据尾部：读写模式截断，只读模式忽略并报告。
   - 两个有效 Snapshot 之间的损坏视为中间损坏，必须失败，绝不跳过。
4. SyncCommit 在 `.rpk` sync 开始之后出现的错误以 `CommitError{Unknown:true}`
   表达；调用者查询 SnapshotID 而非盲目重放非幂等业务。

## 后果

- 恢复状态机只需要一个方向的事实来源，逻辑确定且幂等。
- 缺失或损坏的 `.rpi` 可用显式 `RebuildIndex` 或普通 Open 修复。
- `.rpk` 在 v1 中不得原地覆盖（除恢复截断无效尾部）。

## 备选

- 双文件联合提交标记：恢复需两文件交叉核对，复杂度高于收益。
- 以 `.rpi` 为权威：索引重建成本被错误地放大到每次打开。
