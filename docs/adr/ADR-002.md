# ADR-002：元数据是引擎存储的数据，引擎不内建强类型语义

- 状态：已接受（2026-09-06 修订，取代原"强类型 API 与通用 TLV 边界"；2026-09 v1.2 前精简：通用元数据公开通道整体移除，见决策 2a）
- 关联规范：METADATA_FORMAT_V1.md；GO_API_DESIGN.md §4

## 背景

最初的 v1 计划在引擎核心内建 13 类核心元数据模型（Header、Table、Column、
PrimaryKey、Index、UniqueKey、ForeignKey、AutoInc、TableComment、ColComment、
View、Function、VirtualColumn）及数据库方言→TypedTuple 类型映射。但数据库
备份工具采集到的表结构、约束、注释等，本质上只是一批有字段的记录——对引擎
而言它们就是普通数据。把 13 类结构、字段编号和方言猜测冻结进引擎核心 API，
既过度设计，又让引擎错误地承担了"理解数据库语义"的职责。

## 决策

1. 引擎核心不再内建强类型元数据模型，不提供 `CoreMetadata` / `PutCoreMetadata`。
2. 元数据通过通用记录通道存储（无类型 TLV，保序、无损往返、未知字段透传），
   真实数据库的表结构、约束、注释等作为普通数据写入，引擎不解释其语义。
   2a.（2026-09 v1.2 前精简）通用通道不再公开为 API：原 `PutMetadata` /
       `Metadata` / `ListMetadata` 为只写半成品（无读取侧、零测试），已整体移除；
       TLV 机制下沉至 `internal/metadata`，仅供 `DefineSchema` 自产自销的
       Table/Column 记录使用。未来如需透传，以完整读写 API 一次性设计。
3. 行解码所需的最小 Schema 契约由 `DefineSchema` 提供：它把列名 + TypedTuple
   类型 + nullable + scale 写成 Column 元数据记录，类型字符串是引擎自产自销的
   规范值（`uint64`、`string`、`decimal`…）。引擎只认识这些规范字符串，**不**
   猜测任何数据库方言（`bigint unsigned`、`NUMBER`、`VARCHAR2`…）。
4. 引擎遇到无法解释类型字符串的元数据记录时，把它们当普通存储数据，跳过
   SchemaIndex，绝不因不认识的元数据导致 Open 失败。
5. 13 类核心 RecordType 编号（1–13）与字段布局保留为格式层面的约定，供上层
   数据库适配器参考使用；若上层需要强类型模型与方言映射，应在引擎之外的
   独立适配层实现，按真实 DB fixture 数据设计，不冻结进引擎。

## 后果

- 引擎与"数据库是什么"解耦：新增数据库类型、方言差异不影响引擎。
- 元数据与行数据共用通用 TLV 存储路径，语义解释交给上层。
- 引擎保留 `DefineSchema` 这一最小解码契约，行仍可被 TypedTuple 正确解码。

## 备选

- 内建 13 类强类型模型：引擎被迫猜测方言类型、冻结未知会改变的字段映射。
- 完全无 Schema 契约：行解码布局由调用方每次传入，调用负担过重。
