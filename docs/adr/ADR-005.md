# ADR-005：排序 Row Index Page 编码与 Fence 目录原型（S3-⑦ 前置）

- 状态：已接受（2026-09-09）
- 关联规范：[FILE_FORMAT_REFACTOR_PLAN.md](../FILE_FORMAT_REFACTOR_PLAN.md) §7 / §15，
  [BINARY_FORMAT_V2.md](../BINARY_FORMAT_V2.md) §6
- 决策点：§15 #2（Index Page 2048 vs 4096 条）、#6（Index Page 是否复用数据压缩级别）
- 原型：`internal/index/page_proto.go` + `page_proto_test.go` + `page_proto_bench_test.go`
- 复现：`go test ./... -run '^$' -bench 'BenchmarkIndexPage' -benchmem -count=1 ./internal/index/...`
  原始输出归档至 `docs/baseline/bench-index-page-proto.txt`

## 背景

S3-⑦ 需要把 Row Index 从 v1 的逐行 40B `RowIndexEntry` 改为「排序 Row Index Page +
稀疏 Fence」（§7.1 / §7.2）。§15 明确：未经测量不得冻结常数。本提交只做**纯内存原型**
（编码器/解码器 + 基准 + 单测），**不落盘**——不触碰 `internal/fileformat` 的 IndexTxn/
IndexChunk 目录结构，不接入 writer/reader/recovery，不改任何 on-disk 字节布局或 golden。

原型输入为已按 `(TableID, RowID)` 升序的 `[]ProtoRowEntry{TableID uint32; RowID uint64;
BlockID uint64; RecordOrdinal uint32; ChangeType}`。为原型的忠实度，故意**未建模
PageOrdinal**（数据页在块内的序号）——最终格式 §7.1 还要编 `PageOrdinal run/delta`，
其编码留给 S3-⑦ 落盘提交；原型只记录 `(BlockID, RecordOrdinal)`。

## 候选实现（§7.1 的具体宽度/布局）

定长 **64 B** 页头（与 RowsPageHeader 同构）承载各流长度与 Page CRC：

```text
offset  size  field
0       8     MagicIndexPage "RPKIDXPG"
8       1     version=1
9       3     reserved (0)
12      4     EntryCount
16      4     TableRunBytes
20      4     RowIDBytes
24      4     BlockRunBytes
28      4     OrdinalBytes
32      4     ChangeBitsBytes
36      8     FirstRowID
44      8     MinRowID
52      8     MaxRowID
60      4     CRC32C（覆盖 [64:] 流区）
```

五条流（逐条目编码）：

| 流 | 编码 | 宽度/边界处理 |
| --- | --- | --- |
| TableID run | `uvarint(tableID) + uvarint(runLen)`，每个连续相同表一段 | run 长度 1..剩余 |
| RowID | 每条**表 run 首条绝对 `uvarint`**，其后 `uvarint(非负 delta)`；表切换重新采绝对值 | 用非负 uvarint 而非教科书 zigzag（见下） |
| BlockID run | `uvarint(blockID) + uvarint(runLen)`，连续相同块一段 | run 长度 1..剩余 |
| RecordOrdinal | 首条绝对 `uvarint`，其后 `zigzag uvarint(delta)`（可负，块边界会归零） | 结果校验 ∈ [0, MaxUint32] |
| ChangeType | 每条目 2bit：0=Insert 1=Update 2=Delete，3 保留非法 | 非法值报错 |

**RowID 为何用非负 uvarint 增量而非 zigzag**：输入已按 `(TableID, RowID)` 升序，表内
RowID 严格递增故 delta ≥ 0。若用教科书 `zigzag(int64(r[i]-r[i-1]))`，当两值横跨
uint64 全范围（如 0→MaxUint64，delta=MaxUint64）时，`uint64` 相减的结果转成 `int64`
变为 -1，`zigzag` 后错误编码为 1——跨 delta 溢出丢失。直接以**非负 uvarint** 编码增量
（升序保证无下溢）可正确表达全 uint64 范围。单测 `TestIndexPageRowIDBoundaries` 覆盖
0 / MaxUint64 / 跨 delta 溢出。

Fence 目录条目（§7.2）定长 packed **52 B**（无 struct padding）：SnapshotID(8, 原型常量
0) + TableID(4) + MinRowID(8) + MaxRowID(8) + StoredOffset(8, 目录/最终格式赋予) +
StoredSize(4) + RawSize(4) + EntryCount(4) + PageCRC32C(4)。

## 测试数据（同机同口径，200k 行，固定种子）

三套负载（顺序 / 乱序 / 小 DELTA）均已在编码前按 `(TableID, RowID)` 排序；构造不计入
计时。decode 口径不含 zstd 解压（zstd 在页级独立完成），且原型 decode 会物化
`[]ProtoRowEntry`（≈11.4 MB/op / 588 allocs@200k，真实 Eager 路径是直接流式写 SoA shard，
不会物化，故 decNS/entry 为原型上界）。

## 决策

**#2（Index Page 条目数）= 4096。** 依据：

- 三负载 storedB/entry 一致更低：seq 0.0483→0.0242（几乎减半）、rand 3.214→3.120、
  delta 0.9752→0.9228；更大页把 64B 页头与固定 RLE 结构摊薄。
- `fenceB/row` 减半（0.0255→0.0127），`pages/1M` 减半（98→49）：Open 常驻 Fence 内存
  与页抓取次数直接减半，热点读跳转成本更低。
- encNS/entry 不升反降（seq 12.25→10.87、rand 45.29→43.43），decNS/entry 基本持平
  （seq 13.54→13.16、rand 21.43→21.16，差距在噪声内）。
- 更极端地，1M 行时 4096 条 Page 每页约 3.1 B stored ≈ 12 KB stored / 21 KB raw，冷读
  拉一页成本仍很低。

> 反面：2048 在 rand 的 decNS/entry 略优（21.18 vs 21.44，~1%，在噪声内），且更多页
> 可让单页误读更碎——但被 2× fence 内存、2× 页抓取与更大 stored 大小抵消。不做 8192：
> 虽然 stored 更低，但单页 21 KB raw 的随机解压/缓存污染倾向及「每页恰为一块/一表」的
> 自然粒度更差，且 enc/dec 收益已趋缓、页头摊薄已达极致，故选 4096（设计初荐区间上界）。

**#6（Index Page 压缩级别）= 复用数据级别（`DefaultCompressionLvl=3`）。** 依据：

- level 3 的 storedB/entry 是所有候选里最低（3.120）；level 6（3.134）无存储收益反而
  +18% 编码 CPU（50.63 vs 42.93 ns/entry），level 1（3.258）省 ~24% 编码 CPU（32.59）
  却多 4.4% 存储。
- Index Page 每个 Snapshot 只写一次，且相对数据块是极小体量；其编码 CPU 相对数据提交
  可忽略。因此带副作用的是**存储大小**（影响读路径与文件大小），而非 Index 编码 CPU。
  level 3 给出最优存储且是数据块默认级别，一处复用避免两套压缩配置。
- level 6 对这类小页（几千字节）无增益（小输入下更高 level 找不到更多匹配），故不必为
  Index 单独调高级别。

## 后果

- 本提交**只含原型**：`internal/index/page_proto.go`（编码/解码/Fence）仅被本包单测与
  基准引用，未接入 writer/reader/recovery，未改动 `internal/fileformat` 目录结构，
  on-disk 字节布局与 golden 不变（`shasum -a 256 testdata/golden/*` 前后一致）。
- 设计编码相对现状 chunk delta 更紧凑：seq/delta 节省 ~43%（ratio 0.57），rand 节省
  ~13%（ratio 0.87），为「设计编码 vs 现状 chunk 编码」提供选型证据（写路径改用排序页
  有理，且天然支持 §7.1 的新定位 `(BlockID, PageOrdinal, RecordOrdinal, ChangeType)`）。
- Fence 52 B/页（packed），在未压缩页目录中常驻；Open 只加载 Fence 即可按 RowID 二分定位
  Index Page（Lazy 模式基础）。

## 明确未做（属于后续提交）

- 把 Index Page 写入 IndexTxn / 新建 Row Index Page 落盘格式（S3-⑦ 落盘）。
- Fence 常驻化 / Fence 目录落盘（S4）。
- 接入 Eager/Lazy 读路径、`index.View` 从 `rowShard` 切换到排序页 + Fence。
- PageOrdinal 编码（原型未建模）。
- 多表页的 Fence 语义（单表页占绝大多数；跨表页的处理留给落盘提交）。

## 备注（#3 一致性）

决策点 #3（Eager shard 编码）已在 §9.1.2 定稿为**列式 SoA + BlockID run-length**
（约 13 B/row）。本原型的分页编码/解码与 Fence 均假设 Eager shard 仍是 SoA/block-run；
本提交不重开 #3。

## 落盘实现（S3-⑦ 落盘②，接替原型）

本提交把 IndexTxn 正文的行索引部分从 v1 chunk delta 切换为**排序 Row Index Page +
Fence Directory**，并把 Eager 读路径改为从 Index Page 解码直建 SoA/block-run shard。
原型的上文决策 #2（4096 条/页）与 #6（复用数据压缩级别 `DefaultCompressionLvl=3`）在此落盘时
照搬；以下的实现决策是对成稿字段布局与编码细节的补充。

### 正文布局（冻结）

```text
[IndexTxnHeader 80B]
[SnapshotChunk]                 // 定长 72B（加密 +16B tag），chunk seq 0
[MetadataChunk] × A             // 定长条目，chunk seq 1..A
[BlockChunk] × B                // 定长条目，chunk seq A+1..A+B
[ChunkDirectory]                // 明文，A+B+1 条 ×32B
[IndexPage] × N                 // 每页独立 zstd（level=3），加密 +16B tag
[RowIndexFenceEntry] × N        // 明文 52B，由正文 CRC 认证
[IndexTxnFooter 80B]
```

- 排序键保持 `(SnapshotID, TableID, RowID)`；**逻辑位序保留 ItemOrdinal（=原型 RecordOrdinal）**，
  不引入 PageOrdinal——切片/`ResolveRow`/`RowIter` 走 S2 的 `ItemOrdinal→PageOrdinal` 路径不变。
- 页内编码与原型 `encodePage` 一致：TableID run、RowID 表内非负 uvarint delta、BlockID run、
  ItemOrdinal zigzag delta、ChangeType 2bit；页头为冻结的 `fileformat.RowIndexPageHeader`，
  页 CRC 覆盖流区。
- 每页 `RowIndexFenceEntry` 携带 `SnapshotID/TableID/Min/MaxRowID/StoredOffset(正文内)/
  StoredSize(压缩+tag)/RawSize/EntryCount/PageCRC32C`；Fence 明文、不单独压缩。

### 如何记录页数（决策：header reserved 字 12..16）

任务建议用 offset 76..80（`IndexTxnKeyEpochOffset`），但该 4 字节在加密 store 里已被
KeyEpoch 占用（`PatchIndexTxnHeaderForStorage` 会把 KeyEpoch 写进 76..80）。若把
`RowIndexPageCount` 也放 76..80，加密 store 会被覆盖。因此本提交**改走 offset 12..16**
（`IndexTxnHeader` 里 size(8..12) 与 TxnSequence(16..24) 之间的空闲 reserved 字），
加密与明文 store 一致；`IndexTxnHeaderRowIndexPageCount` 单测锁定该字与 KeyEpoch 字互不干扰。
页数必须 ≥0 且 ≤ RowEntryCount（每页 ≥1 条），解析器在分配前按正文长度截断（防伪造巨页数
触发无界分配）。

### 加密对齐（R11）

本提交以明文优先实现；加密 store 里，每页压缩后按 **Index 域 chunk nonce/AAD** 密封：
复用现有 `ChunkCrypto.Seal`，chunk kind=`IndexChunkKindRow`（行索引页面，不再有 row chunk，
无歧义），chunk seq = 页数前的连续编号（chunk seq 之后继续，避免与 snapshot/meta/block chunk
撞 nonce），`firstOrdinal`=页序号，AAD 绑定 raw/stored 长度与 txn/snapshot。Fence 保持明文，
由 footer 正文 CRC + SnapshotFooter 的 IndexTxnCRC32C（覆盖 stored 字节）认证。
加密 store 的 `encrypted-store.rpk` golden 重新生成并验证（`TestGoldenEncryptedStore`）。

### 代价与回归

- 页压缩粒度是 4096 条/页；Fence 目录 O(N) 常驻，N≈rows/4096（1M 行 ≈ 245 页）。
- 读路径 `parseRowIndexPages` 逐页 OPEN(解密)+decompress+decode，把条目直写 `TxnSink`
  （Eager 直建 shard），不物化 `[]RowIndexEntry`（S3-⑧ 保证 ~13 B/row）。
- 旧 `rowEncoder`/`decodeRowChunk` 成为死代码，留给 S5 删；工厂不调用，读路径遇到
  `IndexChunkKindRow` 直接拒绝（双格式分派禁止）。
